Access Control

Exact invites bootstrap access; short-lived Access Leases authorize every open; revocation fences access at advancing epochs.

Life of an authorization

Revocation

# An invite that was never redeemed (JTI or the full token)
$ tubo revoke invite <token>          # fenced at the redemption boundary

# An already-accepted invite (its Pipe is resolved from redemption evidence)
$ tubo revoke invite <jti>

# All access to a Pipe: advances the authorization epoch
$ tubo revoke pipe-access pipe/myapi
  • pipe-access revocation advances the epoch: accepted relationships and outstanding leases become stale immediately; a fresh share + connect re-authorizes at the new epoch.
  • Revocation checks happen before any target dial and fail closed on unavailable state.
  • A revoked-not-yet-redeemed invite never burns: redemption denies with zero state mutation.

Determinism

Exactly one authoritative accepted relationship exists per (Pipe, recipient). A newer invite for the same pair replaces it; the same recipient retrying never regresses it; a different recipient fails closed. Obsolete invite revocations are harmless; revoking the current invite's JTI fences renewal.
